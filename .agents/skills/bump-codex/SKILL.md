# Bump Codex

Update the repository's Codex compatibility work to a verified stable release. Implement necessary fixes, and **also upgrade the Code Mode host binary whenever a newer compatible stable host is available**. Keep optional feature adoption separate; use [leverage-codex](../leverage-codex/SKILL.md) for deeper opportunities. Do not update an installed Codex CLI, global Pi installation, or installed extensions, run paid inference, or commit unless requested. Preserve unrelated working-tree changes.

Paths below are repository-relative unless stated otherwise. Follow `AGENTS.md` and affected package instructions.

## Establish targets and provenance

- Resolve the latest official stable `openai/codex` release from release metadata, excluding drafts and prereleases, and verify its tag and full commit. Honor an explicitly requested target or comparison range. Do not infer the release from the installed CLI, npm, upstream main, cached HEAD, or tag sorting. If a release cannot be verified, state the blocker rather than claim a latest-release bump.
- Use `~/.cache/checkouts/github.com/openai/codex` as a reusable read-only source cache. Partial-clone it if absent and fetch missing refs; inspect with `git show`, `git diff`, or temporary extraction. Never switch, reset, or edit the shared checkout.
- Inventory the actual baselines in `pi/extensions/experimental/codex-provider/` and `pi/extensions/experimental/subagents/`: `UPSTREAM` and copied-code provenance, reviewed behavior and model catalogs, generated fixture pins, and `code-mode/host-assets.ts`. Follow other Codex-derived consumers where relevant. These revisions are independent; check ancestry before treating a diff as an upgrade. If a baseline is newer than or diverges from the target, compare the relevant trees directly, preserve already adopted behavior, and record any changes as selective adoption rather than automatically rolling back. Do not replace historical citations or copied-code revisions merely to make every reference match one tag.
- Independently check for a newer stable release carrying a `codex-code-mode-host`, even when the source baseline is already current. Unless the user constrains the host target, consider newer stable host releases from newest to oldest; require assets and official SHA-256 digests for every platform in `code-mode/host-assets.ts` (`HOST_ASSETS`). Record each considered tag and commit. A newer CLI npm package alone does not establish host availability.
- If the target has already been reviewed and adopted on the relevant surfaces and no newer suitable host is available, report that rather than manufacture an upgrade.

## Review and implement compatibility

- Inspect release notes and the complete changed-file inventory between each applicable baseline and target. Trace relevant source and tests to local consumers rather than relying on changelog summaries or a green type check. For provider contracts, consult `codex-provider/docs/codex-baseline.md` and `docs/design.md`; for collaboration, consult `subagents/docs/protocols.md`, `docs/codex-parity.md`, and the relevant sections of its pinned reference documents. Follow source links and package `AGENTS.md` as the affected work requires.
- Prioritize model-facing requests, tool schemas/results and placement, transport, replay/compaction, models and feature gates, delegation, lifecycle, and persistence. Distinguish required compatibility fixes, intentional Pi differences, inherited behavior, and optional features. Confirm that a feature is stable and usable through this repository's pinned Pi APIs; do not reproduce Codex internals that Pi cannot execute truthfully.
- Implement required fixes and regression coverage at the smallest meaningful layer. Update active baselines, parity rows, fixtures, and documentation to reflect what was actually inspected or adopted. Change copied-source `UPSTREAM` revisions only when the corresponding adaptation changes; preserve feature-specific provenance. If refreshing subagent contracts, update the extractor's source pins before regenerating its fixture, then run its `--check` mode. Do not advance provenance on the strength of a generated fixture alone.
- Follow [Code Mode host upkeep](../../../pi/extensions/experimental/codex-provider/docs/codex-baseline.md#code-mode-host-upkeep) to update the exact pin and checksums for every supported platform together, review protocol changes, run the real-host check, and record the checked release and runtime platform. If a candidate lacks required assets or fails compatibility validation, record why and consider the next newer-than-current stable host release rather than silently treating the latest as compatible. If none qualifies, retain the working pin and report the host bump as incomplete.

## Verify and hand off

- Run affected package unit/integration/smoke tests and checks, plus the subagents fixture `--check` when its pins or model-facing contracts are touched. Run `vp run @clanker-stuff/codex-provider#check:code-mode-host` for a host bump; this downloads and exercises the actual pinned binary without inference. Run `vp run ready` for cross-package changes when practical. Fix upgrade-caused failures and report unrelated or blocked checks explicitly. Do not substitute paid live canaries for local validation.
- Review the final diff. Report the checked release/tag/commit, each adopted baseline, the Code Mode host transition (or why it could not be completed), behavioral changes, checks actually run, and remaining risks. Make a differing source and host target explicit, and note that running Pi processes need `/reload` or a restart after a host pin change. Briefly list worthwhile optional opportunities for [leverage-codex](../leverage-codex/SKILL.md), carrying forward the exact comparison refs. Do not conflate this source/host upgrade with native Codex evaluation CLI images: new evaluation series resolve and freeze their own published CLI version under `AGENTS.md`.
