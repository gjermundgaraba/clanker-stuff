# Codex provider design

This extension is the always-on `openai-codex` provider for the controlled Pi installation defined by the [supported source baseline](codex-baseline.md). It owns normal Responses requests, Codex-native direct tools and Code Mode, fast-mode service-tier selection, SSE and WebSocket transport, model metadata, turn state, continuation, remote compaction V2, and durable checkpoint replay. It reuses Pi's ChatGPT OAuth implementation and public Responses serializers.

The implementation follows the compatibility objective and pinned [Codex and Pi source baseline](codex-baseline.md). It supports only provider `openai-codex` with API `openai-codex-responses`; it is not a generic OpenAI or Azure provider.

The [2026-09-13 upstream review](upstream-review.md) records the historical audit and subsequent implementation. Initial/offline discovery now lists Astra. Account ownership changes reset account-owned routing, cached sockets, continuation, prewarm, and transport fallback before subsequent requests; bearer rotation for the same account preserves turn routing.

The default entrypoint composes `registerCodexProvider()` from
[`registration.ts`](../registration.ts) with the Codex tool
controller. API-only evaluations use that same provider registration without a tool
controller, rather than intercepting Pi's registration or activation methods. The
normal entrypoint retains the same lifecycle registration order.

The provider runtime is not optional. Loading the extension replaces Pi's effective `openai-codex` provider for the process. The extension must resolve last so no later context, header, payload, provider, or compaction registration can invalidate its checks; see [local deployment](local-deployment.md).

One cached provider session exists per ordinary Pi session. A user turn gets fresh turn identity and turn-state routing, while a cached physical WebSocket, validated continuation candidate, sticky SSE fallback, and context-window generation may survive across turns. A continuation candidate is created only after Pi finishes a successful `AssistantMessage`, using the same public Responses converter that reconstructs the next request. It is an ephemeral prefix validator bound to the current open physical socket, not stored provider history. Session shutdown closes transport state. Account switches detach the previous account record before constructing HTTP, WebSocket, prewarm, or compaction requests, so late callbacks cannot restore the old routing state. The context-window identity remains attached to the Pi session.

Fast mode starts disabled. `/fast` or `--fast` enables the `priority` service tier for supported models across normal requests and native compaction. A root provider publishes successful priority-or-standard changes through the collaboration session contract. Existing, new, and reloaded child providers read that tree-scoped value before each model request or compaction, so the next request step follows the root without rewriting child settings. Only the persisted local preference is global and durable. The provider applies the [upstream tier-routing contract](codex-baseline.md#verified-revisions) to every supported `openai-codex-responses` stream: fast requests set `service_tier: priority` in the body and `tier=priority` in `x-codex-routing-hint`, while standard requests omit both tier selections. This covers SSE requests, remote compaction, WebSocket handshakes, and prewarm. Separately, the local provider sends `originator: pi` for standard requests and `originator: codex_cli_rs` for priority requests. That split is an empirically motivated Pi adaptation, not an upstream routing requirement.

Live model metadata is authoritative; the pinned fallback catalog covers offline startup, including a listed Astra profile with Responses Lite, V2 collaboration, Ultra at `xhigh`, a 272,000-token context window, and 128,000-token maximum output. Hidden models retain their metadata for explicit model selection and resume but stay out of the model picker; a live `visibility: list` makes them available there. Persisted remote catalogs are bound to the ChatGPT account that produced them and are invalidated before another account can observe their entitlements or model policy. A catalog-observed account change also invalidates account-scoped usage cache and in-flight usage publication. The lightning status appears only when the selected model supports fast mode.

Remote publication and account-cache restore preserve matching Pi built-in `inputLimits`, including image resize policy. These limits come from the current Pi model definition, not stale cache metadata; unknown remote models receive no invented limits. Pi's registry still owns `models.json` overrides.

Remote reasoning presets are intersected with Pi's known thinking levels instead of being forwarded as request values. Only the Codex Responses wire efforts `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, and `max` reach transport. Because Pi has no distinct `ultra` thinking level, the provider keeps Ultra as branch-scoped state and resolves its concrete inference effort from a Pi-representable `multi_agent_reasoning_effort`, then Max, then the highest supported Pi-representable non-Ultra effort, with Medium as the final fallback. It also honors a catalog-supplied mode hint or proactive policy, wrapping nonempty custom text in `multi_agent_mode` markers; an empty string suppresses the policy block, and a missing policy uses the audited built-in text. The companion `subagents` extension owns the unchanged V2 tools and child lifecycle; a synchronous session contract carries active and inherited Ultra plus root Fast state between them.

Supported Codex models honor every explicit native `tool_mode`: `direct` exposes `exec_command`, `write_stdin`, `apply_patch`, and `view_image`; `code_mode` exposes those four tools alongside `exec` and `wait`; `code_mode_only`, including Astra, exposes only `exec` and `wait`. An explicit mode overrides the manual preference, and `/code-mode` reports the required policy without changing it. With no recognized selector, `/code-mode` toggles between the four direct tools and `exec`/`wait`, starting in direct mode. That manual preference survives switching through models with explicit modes. The provider activates the appropriate set and suppresses Pi built-ins while it is active, but leaves unrelated extension tools alone. It does not coordinate with tool pickers or persist per-tool choices; its normal lifecycle hooks may replace changes made by other extensions. Idle input normalizes tools before Pi captures the system prompt and selected-tool metadata; steering and follow-up input during a running turn leave the tools unchanged.

Pi normally omits its loaded-skill catalog when `read` is unavailable. When the provider's direct or Code Mode tool set suppresses `read`, the provider restores that catalog as the prompt's `skills` section, with guidance naming the active file-capable tool, so Pi diffs and replays it like its own sections instead of forcing a replacement prompt. Code Mode keeps its live schemas and guidance in the `exec` description rather than a separate prompt section. An extension that forces the whole prompt replaces every prompt section in that request, including the skill catalog, while Pi keeps recording the structured sections in the transcript. The loader follows the current tool inventory after policy refresh, even when the event's prompt options still describe the previous inventory. It does not discover or load any additional skills.

Tool policy resolves the selected provider/model ID against Pi's current model registry at the start of each user turn. Background catalog refresh can replace registry entries without replacing the session's selected model object; the next turn therefore applies the refreshed policy without reselection. Running-turn compaction keeps that turn's tool-policy snapshot. Commands also consult the current registry.

Execution settings have a narrower, per-request lifetime: the provider associates its copied request model and final wire reasoning effort (mapped to Pi levels) with the completed response's tool-call IDs. The tool snapshot overlays the current catalog's output-token limit at request entry, because the selected model can predate a catalog refresh; later refreshes affect subsequent requests without altering the in-flight policy or replacing request identity, routing, and pricing. The extension-instance-owned store hands each association to its executing tool once, keyed by session and call ID; turn/session boundaries clear leftovers and fence late responses. Compaction and isolated auxiliary sampling never publish tool associations. This avoids sampling live context getters after Pi has already fixed its request settings. Direct invocations or calls produced by other providers use execution-entry settings instead; this fallback is not an originating-request guarantee. Direct shell execution and polling capture output policy before any asynchronous work; process completion cannot pick up a newer catalog policy. Code Mode retains each cell's originating model/effort across yields while refreshing its wait-time UI/session context. Wrapping a context with the identical settings is idempotent; rebinding to a new live context still creates a new wrapper. The provider separately copies its request model, scalar options, and caller-owned header values before asynchronous transforms; compaction also copies caller headers before transport work. Header additions, edits, deletions, and null suppression cannot drift across payload hooks, WebSocket attempts, or SSE fallback. Cancellation signals, callbacks, and injected transports intentionally retain their live identity; this is not a deep snapshot of every option object. Pi's own loop supplies each next step's model/effort snapshot; other extensions' tools remain host-owned. Lifecycle checks continue to reject stale branch/model/settings changes during compaction rather than installing a mismatched checkpoint.

This is not Codex's experimental reasoning-history pinning. In **0.155.0**, `ReasoningEffortOverride` is under development and **disabled by default**; when enabled, it requires trusted native `configuration_update` history items in Responses Lite in addition to a pinned request effort. Pi has no native representation for those items. This extension still sends the selected supported effort and does not claim native reasoning-history support. Merely pinning the request field would silently ignore the user's new effort and is not a correct substitute.

`exec_command` and `write_stdin` apply requested `max_output_tokens` with Codex's UTF-8 approximate-token, head-plus-tail formatter and a model-visible truncation warning. The active catalog model's truncation policy caps the request. Only raw command output consumes that budget; Pi process status, truncation-file notices, and the session ID remain visible outside it. This matches the pinned truncation algorithm and control-metadata safety, not Codex's complete PTY result layout. In Code Mode, a nested tool with a declared output schema must return valid model-visible JSON; the provider decodes that JSON to the callable value and never substitutes host-only `details`.

Background tasks and connected MCP tools opt into model-dependent placement through the shared contribution package. See [contributed tools](contributed-tools.md) for dynamic discovery, content envelopes, accounting, and the aggregate permission boundary. User interaction, V2 agent control, and MCP management remain direct.

Code Mode does not select a request envelope. `use_responses_lite` from native model metadata alone determines whether the same active tools and instructions use Responses Lite or the standard Responses envelope. Responses Lite always starts with an `additional_tools` item and gives it and the developer-instruction item deterministic, thread- and payload-sensitive UUIDv5 IDs, so retries, prewarm, continuation, and resumed requests preserve prefix identity.

## Status and observability

`/codex-provider` renders a read-only report from the current Pi context, checkpoint entries, and the extension's SQLite observations. It distinguishes the active branch from the complete session tree, summarizes valid checkpoint usage and estimated reduction, compares the two latest request fingerprints and cache usage, reports replay blocks, actual SSE fallback use, and failed compaction requests, and checks the active checkpoint against the current provider identity. The report is shown through Pi's notification UI and is never appended to the session.

Complete checkpoints remain in Pi's session JSONL because Pi and the extension need them to reconstruct context during branch navigation, reload, resume, and session sharing. Compact request, transport, framing-failure, and compaction-attempt observations are written best-effort to `data/codex-provider/codex-provider.sqlite` under Pi's agent directory. The database uses WAL, never waits on a busy writer, and deletes observations older than 30 days when opened. `--no-session` keeps observations in memory. Observation failure never delays or fails a model request.

Normal-call transport observations separate WebSocket handshakes and prewarm sends from inference dispatches. Attempted inference transports record only ordinal, transport, continuation mode, `response.created` state, failure class, and final recovery decision. They never record wire request/response IDs, content, headers, credentials, or endpoint details. An inference dispatch is counted only after `WebSocket.send()` returns or `fetch()` returns its promise. Handshake attempts and failures include prewarm, while a user abort during an in-flight handshake is not a handshake failure. Sticky SSE activation is recorded separately from the transport actually dispatched; status fallback totals use the latter.

Framing and transport diagnostics are not appended to session JSONL, so they do not travel with copied or shared session files.

The checkpoint entry renderer presents estimated before/after context size separately from provider-reported compaction usage. Its default view contains operational results only; Pi's expanded-entry view reveals checkpoint identifiers, hashes, protocol versions, limits, and retained-item counts. These values establish persistence and replay health, not semantic summary quality.

## Request and transport flow

1. Pi finalizes its system prompt, messages, tools, auth, options, and earlier extension transformations.
2. The provider serializes the effective Pi context with Pi's public Responses converters, then adds only extension-owned Codex metadata. The logical `window_id` is `<session-id>:<zero-based-window-number>`; `context_window_id` is the UUID identifying the current compacted context generation.
3. `context`, `before_provider_headers`, and `before_provider_request` pair the active branch, finalized input, and headers to the same request generation.
4. WebSocket `auto` mode may prewarm once and reuses an idle socket only while its stable handshake identity still matches the endpoint, account credentials, model, effective tier, and other route headers. A mismatch closes the stale socket, reconnects, and clears socket-bound continuation state.
5. On the same open socket, equality of continuation-relevant request fields and the normalized-history prefix permits sending only the new input with `previous_response_id`. The backend owns the referenced response; local normalized items validate only the prefix. Unsupported or ambiguous model-visible projections make the next request full without discarding the reusable socket.
6. On normal inference requests, only an initial `response.created` is held attempt-locally until the next event. It is discarded if that attempt fails first; otherwise it is committed immediately before the next event, which remains fail-closed for replay. Installing turn state from an SSE response header or WebSocket metadata event also makes replay fail-closed. An eligible pre-output WebSocket transport failure makes SSE sticky for that Pi session even when the call-scoped budget prevents same-call SSE dispatch. Fresh inference replay is disabled when `maxRetries` is absent or zero; any positive value opts into a hard cap of one replay shared by continuation repair, WebSocket-to-SSE fallback, and SSE retry. The cap counts inference dispatches only, not pre-send failures or handshakes. Prompt-cache keys and request IDs are not treated as idempotency keys. Pi may outer-retry only failures accepted by its transient classifier; each such retry is a new logical provider call with a new budget.

HTTP Responses (including compaction), model discovery, and the companion usage reader use the shared `@clanker-stuff/codex-http` adapter. It retains only the infrastructure routing cookie `__oailb` in an in-memory cookie jar. HTTPS and the audited first-party ChatGPT hostname allowlist gate both reads and writes; RFC cookie domain/path, expiry, and deletion rules are handled by `tough-cookie`. Authentication/session cookies are never retained, and custom endpoints receive no jar cookies. Explicit caller Cookie headers are not merged with the jar. Automatic first-party HTTP redirects are rejected so manually attached cookies cannot bypass scope checks and redirected response cookies cannot be attributed to the original trusted URL, even when the initial request was cookie-free; explicit manual handling remains available, including compaction's status-aware rejection of redirects. The production jar occupies one package-owned global symbol slot, shared across independent bundled Pi Jiti loaders and reloads in the same JavaScript runtime; factory-created test jars remain isolated. It is discarded on process exit, not persisted or included in observations, and does not change WebSocket handling. Synchronous fetch failures stay synchronous for inference-dispatch/retry accounting.

Redirects are rejected for remote compaction. Normal and compaction streams require terminal protocol state, and compaction additionally requires a matching completed response ID, usage, and exactly one canonical opaque item.

`response.service_tier` is retained for usage pricing. Ordinary responses, compaction, and sampling use the same resolution rule: a missing or `default` response tier inherits the requested tier; any other response tier takes precedence.

## Isolated sampling

The MCP-owned [sampling protocol](../../../mcp/sampling-protocol.ts) defines the type-only contract for `clanker-codex:sampling-scope-request`. This event resolves a request scope from the same lazy runtime serving Pi's model registry. The caller selects the model and resolves registry authentication, then invokes the registry inside `scope.run()` and always awaits `scope.dispose()` in `finally`, including when converting the result fails. Each scope permits one inference and owns its supplied or automatically allocated session ID. Existing Pi session IDs are rejected as collisions. Disposal marks the scope closed, aborts active work, closes sockets, awaits transport settlement, and removes only its records and timers. Late registry dispatch and socket decoding cannot recreate disposed state. Session replacement and shutdown also dispose these scopes.

Sampling accepts text messages without tools, conversation history, or an agent loop. Verified GPT-5-family text uses `o200k_base`, following [OpenAI tiktoken's model-prefix mapping](https://github.com/openai/tiktoken/blob/main/tiktoken/model.py) checked on 2026-09-13, implemented by the pinned `js-tiktoken` dependency. Astra and other model families without a verified mapping are rejected before inference. Budgets must be positive safe integers and are capped at the selected model's maximum output. Deltas are buffered into geometrically growing batches; only batches checked against the token count of the exact concatenated returned text are emitted. This bounds aggregate tokenizer input for delta streams without assuming token counts add across chunks. Authoritative completed messages replace buffered tails and receive the same exact check, including refusals and multiple output items. The caller uses `scope.boundText()` again after stop-sequence slicing, because a shorter text prefix can tokenize to more tokens. Reasoning is excluded from returned content and its text budget; actual reasoning usage remains chargeable and reported.

Reaching the text limit at a batch or completion check aborts the transport and yields Pi's `length` stop reason for MCP's `maxTokens` result. This is a returned-content bound with best-effort generation cancellation, delayed by at most the next batch check. The Codex request sends no assumed `max_output_tokens` field, and there is no claim of a native generation limit, exact backend token ceiling, or billing ceiling. Reasoning and text generated before cancellation can exceed the returned budget. Usage received before cancellation or failure is preserved unchanged, separately from returned content; `scope.status.usageComplete` remains false when no terminal usage arrives, and missing usage stays unknown.

Sampling validates the event envelope before token accounting: `type` must be a string and a supplied `output_index` must be a nonnegative integer; an omitted index retains the existing zero default. Malformed supplied indexes are rejected rather than silently routed to message zero. Delta and output-item payloads are validated against the fields consumed by the bounder, and completed message content is validated as output-text/refusal parts before completion state changes. Validation preserves additional wire fields and does not clean or project events; completion rewriting retains event and item metadata. Unsupported content fails closed.

[Sampling contract tests](../tests/sampling.test.ts) exercise the actual adapter through Pi's registry and authentication with controlled SSE and WebSocket transports. They cover small budgets, chunk and Unicode boundaries, completed items, refusals, partial usage, repeated success/failure/cancellation, conversion failures, overlapping scopes, ordinary session caches, handshake disposal, and late decoding with deterministic timer checks. [Tokenizer work tests](../tests/sampling-bound.test.ts) bound aggregate encoded input as stream size grows and verify buffered output and authoritative replacements. These fixtures establish client behavior, not a live backend generation-limit guarantee.

## Compaction and checkpoint v1

Automatic compaction uses the remote model limit when available, capped at 90% of the context window; the effective window defaults to 95%. Pi owns scheduling, queue delivery, retry, `agent.state.messages` replacement, and the durable `CompactionEntry` whenever `session_before_compact` fires, including the host's between-tool-call threshold check. OpenAI remote V2 supplies the checkpoint content. Inline compaction reuses the active turn transport only as last-mile provider safety when Pi did not schedule compaction, including when the provider-native limit is lower than Pi's threshold. The two carriers are mutually exclusive for one checkpoint.

Lifecycle checkpoints are Pi `CompactionEntry` records identified by `details.type`; inline checkpoints are `CustomEntry` records identified by `customType`. Both identifiers are `codex-provider.checkpoint`, and every new native checkpoint has:

- checkpoint marker `codex-provider.checkpoint`;
- schema `clanker.codex-provider/checkpoint`, version `1`;
- protocol `openai-responses-compaction-v2`;
- provider/API/base-URL identity and the producing model ID;
- exactly one final canonical `compaction` item, recent canonical user messages, and bounded non-final `agent_message` items, excluding descendant-authored progress updates;
- response ID and usage, source-token estimate, reason, phase, and a SHA-256 replacement digest;
- current/previous window IDs, window number, model `comp_hash`, effective token limit, and request-schema version.

The parser requires exact keys, validates every scalar and replacement item, verifies the digest, and deep-freezes a clone. No earlier local checkpoint namespace or version is accepted. Wire `compaction_summary` is accepted only as a provider-output alias and is canonicalized immediately to `compaction`.

Retained user text has a 64,000-token budget using the conservative local estimator. Eligible non-final agent messages must fit individually within 10,000 estimated tokens. Final-answer messages and descendant-to-ancestor `Message Type: MESSAGE` progress updates are dropped; tasks, sibling messages, and ancestor-to-descendant messages remain eligible. Stale tool/reasoning/system/developer items and image bytes are not persisted. Images become small text omissions in the durable replacement; supported inline images may remain only in the transient request that triggered compaction.

## Lifecycle checkpoints

Lifecycle compaction makes one native request and returns its opaque checkpoint to Pi only after source, branch, model, generation, and request-state checks pass. Pi installs and orders the `CompactionEntry`, shrinks live agent context, delivers queued messages, and owns overflow retry. The matching `session_compact` event verifies persistence before the provider window is installed. Both successful and failed Pi terminals release the pending lifecycle operation. Pi's required summary field contains a checkpoint-specific operational marker, not a second model-generated summary. Provider-reported native usage is therefore the complete compaction usage. Custom `/compact` summary instructions do not apply to the opaque native protocol.

Checkpoint phases have one definition:

- `overflow-retry` only for an overflow lifecycle event with `willRetry: true`;
- `mid-turn` when the newest non-custom context message is a tool result and the run will continue;
- `pre-sampling` for other inline checkpoints;
- `standalone` for manual compaction and other lifecycle checkpoints, including overflow without retry.

Compatible Codex replay sends the opaque replacement. Incompatible or corrupt lifecycle checkpoints block sampling; there is no automatic text fallback. Native compaction failure leaves the original context unchanged. A real-session regression also verifies that an accepted prompt which triggers failed inline pre-sampling compaction remains exactly once in the durable branch after reopening the session; no normal inference or checkpoint is installed by that failed attempt. The original JSONL history remains plaintext on disk; the opaque item is not secure deletion.

## Tool display

Rendering is a Pi host representation. Direct renderers live in [`tools/renderers.ts`](../tools/renderers.ts); [`code-mode/renderers.ts`](../code-mode/renderers.ts) composes nested calls without changing tool arguments, execution semantics, or model-facing output. UI-only snapshots are stored in result `details`.

- `exec_command` shows a bash-highlighted command, capped at three screen rows, and its working directory. Results show the last five screen rows, truncation and full-output notices, and exit status with measured duration. Display removes the model-facing metadata trailer because those fields have dedicated status lines. A line-truncation notice appears only when the returned text is the truncated capture; whenever a full-output path is present the text was rebuilt from that file, so the notice is suppressed for new and previously persisted results alike. The pending elapsed timer stops itself once its row is no longer drawn, because Pi rebuilds the transcript on display-setting changes without disposing the replaced rows, and re-arms when a live row is drawn again after Pi pauses rendering for an external editor.
- Every displayed string that did not come from a sanitized process capture, including commands, working directories, patch paths, diffs, full-output paths, and Code Mode cell IDs, is stripped of escape sequences and control characters before styling, so file contents and model arguments cannot emit live terminal controls; single-row headers also flatten newlines. Printed JSON is re-indented token by token rather than parsed and re-serialized, so out-of-range integers, duplicate keys, and exact literals display unchanged. Values nested more than 32 levels deep, or whose indented form would exceed eight times the original length, keep their original layout.
- `write_stdin` shows the session and escaped input, or `(poll)`. Its default preview is three screen rows; expansion restores the complete escaped input, including control characters.
- `apply_patch` shows file actions and add/remove counts. One `PatchChange` shape flows from both the patch text and the applied result: `kind`, `from` for a move, `path`, `changed`, and an optional `lines` pair of added and removed counts that is absent when the count is unknown. The header comes from the patch text while pending and from the result metadata once complete; totals wait for completion because a pending deletion's line count is unknown and are withheld while any completed count is absent; unknown or zero counts show nothing, so a pure rename shows no counts. A header built from arguments the trace budget cut withholds the cut file's counts and marks the file count open-ended. File-list previews are limited to nine screen rows and numbered diffs to twelve, with an expansion hint when more rows exist. Result details retain complete change metadata independently of per-file display diffs. Diffs are keyed by change index, so a patch that touches one path twice keeps both. There is no patch-wide diff budget; each diff is capped per file at a line boundary. Nested diagnostic snapshots can instead omit the entire details value when their shared budget runs out. Display schemas reject missing or invalid metadata rather than inventing counts. `changed` is a direct comparison of the file before and after, so an edited rename whose diff was omitted is never shown as a bare rename, even for a lone change or when fuzzy context matching rewrote lines without plus or minus hunks. An update whose hunks, context lines included, are large enough that a full diff would block the event loop for seconds records metadata without a diff; a small edit to a large file keeps its diff. Deletions count lines exactly by streaming regardless of size, diff only files up to 1 MiB, and never read FIFOs, sockets, devices, or symlinks. That metadata is best-effort: an unreadable file is still deleted and records no count. CRLF patches summarize to the same paths the applied changes report.
- `view_image` shows the path; Pi renders the image itself.
- Code Mode uses Pi's `Box` with a background that follows the worst nested outcome: pending while the script runs, error when the script or any nested command failed, success otherwise. Before any result, the call slot owns the box. Once a partial or final result arrives, the result slot owns the complete box, including the script header when visible, and the call slot becomes empty. Pi still owns image rendering and click-to-expand. It keeps three screen rows of highlighted script beneath its heading until nested traces arrive. The default view then replaces the wrapper with a summary and up to four one-line calls, prioritizing failures, running calls, and recent successes while preserving their relative order. Durations stay on the command row, failure output appears underneath, and the complete collapsed result is limited to sixteen screen rows. One detail hint reports omitted calls, including omitted failures and running calls, and traces lost to the runtime trace limit.
- Code Mode unwraps a printed process-result envelope only when it exactly matches a captured process result. Its output becomes real text lines; arbitrary script output remains visible. Mirrored failed-process output already shown under its command is omitted from the aggregate preview. Expansion restores full scripts, nested results, and original returned values under `Script output`.
- Nested call renderers receive independent state and trace-specific completion/error flags. A later process poll resolves earlier yielded snapshots for the compact summary; an observed exit outranks a concurrent poll that still saw the process running. Invalid persisted arguments render a marker instead of throwing during the draw. Script completion, command failure, running work, and termination have distinct status labels.
- Code Mode separates cell execution context from operation-scoped UI subscriptions. Each outstanding exec, wait, or termination receives live updates; a new subscription immediately displays the retained traces. The host still decides whether overlapping operations are accepted. Every operation removes only its own subscription on success, rejection, or cancellation, so a rejected wait cannot steal another wait’s updates and settled cards remain snapshots. UI callback failures are isolated per subscriber. Wait and termination headers keep the sanitized cell ID visible in both views, alongside elapsed time since the host announced the cell. A single reconciled outcome tally drives status selection and finished/running/failed counts; nested-tool previews retain their own details. No-tool waits distinguish waiting for output from a returned, still-running script and report no new output only for an empty returned envelope with no retained or dropped traces. The trace store owns one record per cell for traces, dropped counts, and monotonic timing; it produces data snapshots, while the runtime delivers UI events. Timing advances on existing events rather than a ticking timer and is cleaned up with cell traces. Historical results without timing omit it. Notifications retain timing and traces without changing their model-facing text. The real-host check covers overlapping wait rejection and cancellation in addition to execution, yielding, and termination.

Rendering has separate preparation and layout lifetimes. Renderer callbacks prepare content on argument/result updates and theme invalidation; script highlighting survives width changes. Patch headers prepare lazily after both slots have run, so completed metadata supplies the first draw, and retain that child until invalidated. The [render components](../tools/render-components.ts) keep only the last width's layout, including complete head/tail previews and hints. Code Mode caches the fully composed box in both collapsed and expanded views: Pi's visual truncation helper lays out the full input before slicing, and its box cache still traverses children and compares every line. Fullscreen scrolling traverses offscreen rows too, so unchanged redraws must not repeat highlighting, full-output layout, nested prefixing, or ANSI width scans. Nested invalidations still reach both delegated slots, and direct pending-process draw tracking remains outside layout caches.

Pi's configured expand key reveals details. ### Diagnostic JSON snapshots

Code Mode trace inputs and details use `safe-stable-stringify` 2.5.0 followed by JSON parsing to produce detached JSON values, not lossless JavaScript clones. Object insertion order is retained. Undefined, functions, symbols, and bigint values are omitted in objects and become null in arrays; unsupported root values and non-finite numbers become null. Dates and custom `toJSON()` projections follow JSON semantics. Cycles become `[circular]`; shared references are copied independently.

Serialization first creates a detached JSON snapshot, with depth limited to 12, breadth and visited values limited to 4096. Individual string bodies are capped at the requested character budget; aggregate retained long-string bodies are capped at twice that budget. Strings no longer than the truncation marker are retained within the per-node marker allowance, rather than expanded into a marker. Clipped strings carry `[value truncated]`. A separate four-budget allowance for visited key characters bounds intermediate allocation; exhausting it or the traversal limit produces `[value limit]`. These are resource guards, not estimates of final JSON size, and can reject inputs with many large omitted keys.

Snapshots that fit their exact serialized allowance are retained unchanged. Oversized snapshots shorten strings longest-encoded-first, breaking ties in traversal order. Each string is considered once; escaped prefix lengths and truncation markers are measured exactly, without splitting surrogate pairs. If even shortening all eligible strings cannot fit the keys, structure, non-string values, and markers, the whole value becomes `[value limit]`. Reduction never revisits original getters or `toJSON` hooks. Exceptions during normalization produce `[unavailable object]`; fixed fallback markers may exceed tiny caller allowances. Renderers must not treat marked patches as complete. Text and image trace budgets remain separate and unchanged.

These are diagnostic retention limits, not a JavaScript execution sandbox: enumeration, getters, proxies, and `toJSON()` execute inside the serializer and can consume time or allocate before the callback runs. A zero character allowance short-circuits before serialization. No partial-object preservation is promised. Direct tool results are not replaced by the bounded diagnostic copy.

## Safety invariants

1. Context framing must find exactly one canonical persisted-to-live match.
2. Only persisted retryable assistant errors omitted by Pi may be absent from live context.
3. Marker-free finalized input must retain complete structural parity and valid tool pairs.
4. Earlier payload and header transformations are paired request-locally and never persisted.
5. Compatible replay requires provider, API, canonical base URL, and non-conflicting `comp_hash`; model transitions compact explicitly instead of treating the model ID as the compatibility key.
6. A stale generation, branch, leaf, model, request state, source hash, race, or unverifiable append aborts the pending request.
7. Observations contain request hashes, 16-hex item hash prefixes, model/options, transport and retry outcomes, timings, identifiers, and usage; never message text, tool arguments, headers, credentials, URLs, or encrypted checkpoint content.

The persisted-versus-live proof is detailed in [context alignment](context-alignment.md). Executable coverage lives in the [checkpoint](../tests/checkpoint.test.ts), [provider](../tests/provider.test.ts), [replay](../tests/replay.test.ts), and [lifecycle integration](../tests/lifecycle.integration.test.ts) tests.

## Accepted limits

- Pi cannot atomically replace arbitrary raw provider history and append the matching checkpoint, so append and continuation are separately verified and fail closed.
- Pi exposes load-order chaining, not exclusive terminal ownership. This package is approved only under the audited local load-last contract.
- Pi's effective prompt, tools, permissions, and messages remain authoritative. Codex application world-state sections that Pi does not expose are not fabricated.
- Pi preserves complete reasoning-item JSON, but provider-only message, function-call, and custom-tool metadata outside Pi's `AssistantMessage` representation is absent from full reconstruction after socket loss.
- Context-size and tool-output estimates use conservative UTF-8/4 plus a fixed image estimate. Isolated sampling uses the verified text tokenizer described above and does not reuse that estimator.
- Server sockets, response continuation, and turn state are ephemeral. Durable resume reconstructs a complete request from checkpoint plus Pi history.
